# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Glomi" is a single-page prototype for a live AI makeup coach. A user picks an occasion, Claude generates a step-by-step routine and the shopping list it requires, and then a camera-based "live" screen lets them ask Claude to look at a captured frame and give spoken feedback per step.

The repo is two code files, a setup README, and a small folder of photos:
- `index.html` — the entire frontend: markup, CSS, and vanilla JS all inline in one file. No framework, no bundler, no build step.
- `api/claude.js` — a single Vercel serverless function that proxies requests to the Anthropic Messages API, keeping `ANTHROPIC_API_KEY` server-side.
- `README.md` — end-user instructions for uploading this repo to GitHub, deploying it on Vercel, and wiring up the API key/domain. It is not developer documentation.
- `images/looks/` — real photos used as the occasion chips' photo thumbnails on the setup screen (see the Setup screen entry below). Static files, served as-is by Vercel; no processing pipeline.

There is no `package.json`, no dependency manifest, and no test/lint/build tooling anywhere in the repo — there are no such commands to run. Development is just editing `index.html` and `api/claude.js` directly and deploying to Vercel to test.

## Architecture

**Deployment model**: static file (`index.html`) + one serverless function (`api/claude.js`), deployed on Vercel with zero config. Vercel auto-detects any file under `api/` exporting a default handler as a serverless function; `index.html` is served as a static asset. The API key lives only in the Vercel project's environment variables (`ANTHROPIC_API_KEY`), never in client code.

**Client → server → Anthropic flow**: the frontend never calls Anthropic directly. `callClaude(content, model)` in `index.html` POSTs `{ content, model }` to `/api/claude` for every AI call (step generation, live vision feedback, the substitute swap); `model` is optional and omitted (`undefined`) by every caller except step generation. `api/claude.js` reads `content`/`model` from the body, wraps `content` as `[{ role: 'user', content }]`, forwards that to `https://api.anthropic.com/v1/messages` with the server-side key, `model || 'claude-sonnet-5'`, and `max_tokens: 4096`, and relays the raw Anthropic response (or error) back to the client. `content` can be plain text or a mixed array of `{type: "text"}` / `{type: "image", source: {type: "base64", ...}}` blocks — the API function is a thin, opinion-free passthrough, so all prompt construction and response parsing happens client-side. (`api/claude.js` also still accepts a `messages`/`system` shape if sent, used as-is instead of the `content` wrapping, though nothing in the client currently sends that shape — it was built for a multi-turn chat widget that has since been removed.)

**Tab bar**: a fixed bottom `.tabbar` with two tabs — Home, Account — toggles `#home-view` / `#account-view` via `switchTab()` and the `TAB_VIEWS` map, following the same `.hidden`-class pattern as everything else (no router). The tab bar itself is hidden during the focused loading/live-guide flow (`setTabbarVisible(false)`) and restored on the done screen or when returning to setup, so it can't be used to abandon an in-progress guide.

**App state machine** (inside `#home-view`): a single global `state` object (`occasion`, `neededProducts`, `steps`, `currentStep`, `stream`) drives five screens toggled via the `.hidden` class — `#setup-screen` → `#loading-screen` → `#tryon-screen` → `#live-screen` → `#done-screen`. DOM elements are looked up by ID on demand rather than cached. `setupChipGroup(containerId, onSelect)` scopes the occasion chips' "clear siblings, mark active" logic to their own container so it can be reused for other chip groups without them interfering with each other.

**Contact widget**: a floating button (`#contact-fab`, hidden alongside the tab bar during the loading/live-guide flow) opens `#contact-overlay`, a static card with a `mailto:` link and a `tel:` link (currently `purimannat246@gmail.com` / `0899627673`). This replaced an earlier AI chat widget ("Ask Glomi") — that widget's multi-turn conversation, localStorage history, and daily message cap are gone along with it; the contact card is plain markup with no JS beyond opening/closing the overlay.

**Account tab and local persistence**: there is no login system or backend database. Saved routines and reviews are read/written straight to `localStorage` via the `getRoutines`/`getReviews` (and matching `set*`) helpers — data lives on-device only and does not sync across browsers or devices. The Account tab itself has no profile/name/email fields — `getAccount()`'s `name`/`email` are only ever written from the checkout form (below), on the theory that collecting contact details is only worth doing for someone actually paying, not every visitor. "Save this look" on the done screen snapshots `state.occasion`/`state.neededProducts`/`state.steps` into the `glomi_routines` list. "Upgrade" opens a preview checkout sheet (`#checkout-overlay`, styled off the shared `.look-detail-overlay`/`.look-detail-card`/`.look-detail-close` pattern also used by `#review-overlay`) with name, email, and full card-details fields — but the card number/expiry/CVC are deliberately never persisted or sent anywhere; only the last 4 digits are kept in `localStorage` (on `glomi_account.plan`/`cardLast4`) purely for display, the same as what a real processor like Stripe would expose after checkout, while `name`/`email` are saved to `glomi_account` so Pro can recognize the account on return. There is no real billing integration yet — this is intentionally a stand-in for a future Stripe Checkout redirect, not a payment form to be taken further as-is.

**Free-plan limits**: `isProAccount()` (`getAccount().plan === 'pro'`) gates saved guides (`canSaveMoreGuides()`, checked in both `save-look-btn` and `saveReviewedLook()` before writing to `glomi_routines`, capped at `FREE_GUIDE_LIMIT`). This is a soft, client-side check only — there's no server to enforce it, so it's an honest nudge (and a reason to upgrade), not a real paywall; clearing local storage resets it. Hitting the limit shows an inline message with a link that jumps to Account and opens the checkout sheet (`showSaveLimitMessage()`).

**Setup screen**: user picks an occasion chip — there is no product input at all; the app tells the user what they'll need rather than asking. Three chips show by default — Everyday, Going out/Date, Party (`data-occasion` values `Everyday`/`Date`/`Party`) — with "Other" behind `class="chip hidden"` until `#occasion-more-btn` is tapped (a plain toggle over `.classList.toggle('hidden')` — no animation, just a label flip between "▾ More options"/"▴ Fewer options"). Tapping any of the three default chips calls `startGuide()` immediately — there's no separate "start" button for the main path, picking the occasion *is* the submit action. "Other" is the one exception: it can't auto-start with empty text, so picking it reveals `#occasion-other-input` (a free-text field whose value, not the literal word "Other", becomes `state.occasion`, giving the AI real context like "prom" or "photoshoot") plus a `#other-start-btn` that appears only for this path; Enter in the text field also submits. Both `#other-start-btn`'s click handler and the Enter-key handler guard on non-empty text before calling `startGuide()`. Each of the three default chips shows a `.chip-photo` circular thumbnail (a real photo from `images/looks/`, e.g. `clean-girl.jpg` for Everyday) instead of the line-icon `.chip-icon` the "Other" chip still uses — these replaced a separate Looks tab/gallery that used to exist for exactly this purpose (browsing example looks); the photos are purely decorative here and don't change what gets sent to Claude, `state.occasion` is still just the chip's plain label/value.

**Step generation**: on picking an occasion (or "Other" + Enter/the inline start button), `startGuide()` sends a prompt asking for a JSON object with `productsNeeded` (a flat array of product names the routine requires) plus an ordered `steps` array (`title`, `instructions`, `product`, `zone`, `color` per step — `markerCount`/`diagramNote` are filled in afterward, see below) via `callClaude` — since there's no product input, Claude both decides what a beginner needs for the occasion *and* builds the routine around it in one call. This is the slowest single thing that happens anywhere in the app (a real network round-trip generating a full structured-JSON routine before anything can render), so several things specifically target its latency: the call passes `FAST_TEXT_MODEL` (`claude-haiku-4-5-20251001`) instead of the `claude-sonnet-5` every other call defaults to — this call is pure JSON formatting with no visual reasoning, so a fast model produces the same quality output much sooner; `api/claude.js` accepts an optional `model` field in the body (falling back to `claude-sonnet-5`) specifically so the client can make this override per-call rather than sitewide. The prompt itself is also bounded to cap worst-case output length — steps are capped at "typically 8-11, never more than 12" and `instructions` at "max 15 words" — since a longer response is a slower response regardless of model. `markerCount` and `diagramNote` used to be asked of the model per step too; they're now computed client-side from `ZONE_DEFAULTS[step.zone]` right after parsing (a placement-dot count and a templated caption like "2 dots under both eyes" per zone) since both are boilerplate that doesn't need AI judgment — cutting two fields off every step is a real reduction in what the model has to generate, on top of the faster model. The prompt also spells out an intensity/finish guide per occasion (Everyday light and low-maintenance, Going out/Date soft and romantic, Party bold with glitter/shimmer and long-wear or waterproof formulas called out) so the routine actually matches what the occasion calls for instead of defaulting to the same safe, natural look regardless of `state.occasion` — this is prompt text only, not something the client parses or validates. `color` is Claude's best-guess hex shade for that product (a red lipstick → a red, a nude concealer → beige) and is validated with a `/^#[0-9a-fA-F]{6}$/` check before use — an invalid or missing value just falls back to the default pink marker fill rather than breaking rendering. The response is stripped of markdown code fences (`stripFences`) and `JSON.parse`d into `state.steps`/`state.neededProducts`. Claude is expected to return *only* raw JSON — if that contract breaks (extra prose, invalid JSON), generation fails and the user is bounced back to the setup screen with an error message. There is no retry or schema validation beyond the `try/catch`. While the request is in flight, `#loading-text` cycles through `LOADING_MESSAGES` on a `setInterval` (cleared in both the success and error paths) so the wait reads as active progress instead of a stuck spinner — this doesn't reduce the actual wait, only how long it feels.

**Needed products**: `state.neededProducts` renders as plain tags (`renderNeededProducts()`) directly on the live screen, under a "You'll need" label and above the step track — there's no separate shopping-list screen or confirmation step between generation and the camera; `startGuide()` calls `renderNeededProducts()` right after generation and shows `#tryon-screen` next, and `#tryon-screen`'s "Looks good" / "Skip preview" buttons are what actually call `renderStepTrack()`/`renderStep()` and reveal `#live-screen`.

**Try-on preview** (`#tryon-screen`, between loading and the live guide): a live camera "filter" that paints color overlays for lips/eyes/cheeks onto the user's own face, using whatever colors the just-generated routine picked for the `lips`/`eyelids`/`cheeks` zones (`deriveLookColors()` pulls these straight from `state.steps`). This is the one place the app reaches outside itself for code — `loadTryonLandmarkerImpl()` dynamically `import()`s MediaPipe's Face Landmarker from a CDN (`@mediapipe/tasks-vision`, plus its WASM runtime and a `.task` model file from Google's model storage), and if the import/model load fails (blocked network, unsupported device) the screen degrades to a plain error line with "Skip preview" still available, never a dead end. `renderTryonFrame()` runs on `requestAnimationFrame`, calling `detectForVideo()` each frame and drawing the lip/eyeshadow/cheek shapes from the ~468 returned face landmarks via hardcoded index groups (`TRYON_LIPS_OUTER`/`_INNER`, `TRYON_EYE_LEFT/RIGHT`, `TRYON_CHEEK_LEFT/RIGHT`) that are the standard, widely-documented MediaPipe point groups for those regions — they have not been tuned against a real face (no way to verify that in this environment; the geometry helpers below were unit-tested with synthetic landmark data instead, which confirms the math is correct but not that the regions land in the right place on an actual face), so placement may want small adjustments once tested on-device. Raw per-frame landmarks are passed through `smoothTryonLandmarks()` before drawing, which runs each landmark coordinate through its own "One Euro Filter" (`makeOneEuroFilter()`) — the adaptive smoothing technique real-time AR trackers use in production, rather than a flat exponential smooth: it damps hard while a point is roughly still (kills jitter) and automatically lets go during fast motion (kills lag), which a single fixed smoothing factor can't do at the same time. Unit-tested with synthetic landmark data confirms it converges on a still input and correctly re-converges after a simulated sudden jump rather than diverging or freezing.

Sizing and orientation are anchored to the face itself rather than the screen, the way a real AR filter does it, so the effect holds up as someone moves closer to the camera or tilts their head: `landmarkFaceScale()` derives a pixel scale from the outer-eye-corner distance (landmarks 33/263, about the most reliably-cited pair in any MediaPipe reference) and every blur/gloss/glow radius and the eyeshadow's reach are sized relative to that instead of a fixed fraction of video width; `eyeUpVector()` derives each eye's own "toward the brow" direction from that eye's corner points instead of assuming screen-up is correct, so the eyeshadow band rotates with head tilt instead of staying screen-vertical. Every shape is traced with `tracePath()` — a `quadraticCurveTo` through each landmark toward the midpoint of the next segment — instead of straight `lineTo()` between the sparse landmark points; a handful of points joined by straight lines reads as an obvious polygon, and this was the single biggest remaining "cheap canvas filter" tell before it was added. The main fill in each region (the lip fill, the eyeshadow band, the cheek flush) draws with `globalCompositeOperation:'color'` rather than `'multiply'` — canvas `'color'` blend takes hue and saturation from the fill but always keeps the *backdrop's* lightness (it resolves to `SetLum(fill, Lum(backdrop))`), so the video's existing skin shading, highlights and texture creases still show through exactly as before, just recolored, instead of getting flattened under a uniform darkening wash. This also makes the region structurally incapable of crushing toward black: because luminosity is a linear function of RGB, any alpha-weighted mix of the backdrop with a same-luminosity result keeps that exact luminosity too, so the result can only ever be as dark as the video pixel already was, regardless of the fill color or alpha (verified directly by rendering a lit gradient backdrop through both blend modes and sampling pixel luminance — `'multiply'` measurably darkened the whole gradient including its highlight end, `'color'` reproduced the original backdrop's luminance almost exactly at every sample point, even with a near-black fill at alpha 0.9). Liners (the lip edge line, the eyeshadow lash-line liner) stay on `'multiply'` since a liner is meant to read as genuinely darker pigment rather than a hue shift, each still capped by `hexLuminance()` (perceived brightness of the shade) so a very dark routine color can't push the liner itself toward solid black. The main fills also carry a small canvas `blur()` filter so the tint's edge doesn't read as a flat painted patch (`drawTryonCheek()` is the one exception — its radial gradient already fades to zero alpha on its own, so an extra `blur()` pass there was redundant cost with no visible effect, and was removed; canvas `blur()` runs in software on a lot of devices and was a real contributor to on-device lag). Lips get the liner described above, an even-odd fill against `TRYON_LIPS_INNER` so an open mouth doesn't get painted straight over the teeth, and a `screen`-blend gloss highlight; eyeshadow draws as a single soft-edged gradient band (fading from the lash line up toward the brow) plus its own thin liner along the lash line — an earlier version stacked two separate `'multiply'` band passes plus the liner on top of each other, and real-device testing showed this compounding into solid black blocks over the eyes with a dark "Party" shade, which is the failure the move to `'color'` blend (plus the earlier single-pass fix) addresses at the root rather than just capping opacity around it. This is the realism ceiling available in 2D canvas without a trained blend model — still an approximation, not a photorealistic render; a genuinely Snapchat/TikTok-level result would need GPU-based 3D face warping and an ML-trained color model, which is a different technology stack entirely (a commercial AR SDK), not a reachable target for a canvas overlay no matter how it's tuned.

The model download (a few MB) is the slow part, so `prefetchTryonLandmarker()` kicks it off from inside `startGuide()`, in the background, the moment step generation starts — by the time the user reaches this screen the model is usually already loaded or close to it. It caches its promise on `tryonState.landmarkerPromise` so a later call (from `startTryonPreview()` when the user actually taps "Enable camera") just awaits the same load rather than starting over; `startTryonPreview()` also requests the camera and awaits that prefetch concurrently rather than sequentially, since neither depends on the other. `startTryonPreview()`'s `getUserMedia` call constrains the request to `width`/`height: {ideal: 480}` rather than leaving it unconstrained — with no constraint, phones commonly hand back 1080p+ video, and since `renderTryonFrame()` sizes the canvas to the video's native resolution (`canvas.width = video.videoWidth`), that resolution is what face detection AND every multiply/blur canvas fill run against, every frame, for a result ultimately shown in a ~260px circle. Capping the request cuts that per-frame cost roughly with the pixel count, with no visible quality loss at this display size — this (plus the redundant-blur removal above) is the main lever against laggy/jittery on-device tracking, since that's mostly a frame-rate problem rather than a placement one. The camera stream (`tryonState.stream`) is handed directly to the live screen's `<video>` on "Looks good — start the guide" (`enterLiveGuide()`) so the user isn't asked for camera permission twice; "Skip preview" explicitly drops it first so the live screen requests its own fresh stream instead.

**Substitute swap**: on the live screen, "Don't have this? Get a swap" (`#substitute-btn`) sends a one-off `callClaude` text prompt scoped to the current step's product, asking for one common alternative already lying around plus a one-sentence usage tip — rendered into `#substitute-result`, which resets to hidden on every step change (`renderStep()`) so a stale swap suggestion from a previous product never lingers into the next step.

**Live screen**: shows a circular camera preview (`getUserMedia`), the current step's text, and an SVG face diagram (`#face-diagram`) with dot markers placed according to `zoneCoords` (a hand-authored map of named face zones — `forehead`, `brows`, `eyelids`, `under-eyes`, `cheeks`, `nose`, `lips`, `jawline`, `chin`, `all-over` — to `[x, y]` coordinates on a 200×240 viewBox). `getMarkerPoints` spreads multiple markers per zone outward in rings when `markerCount` exceeds the zone's base point count. Steps can optionally be read aloud via the Web Speech API (`speechSynthesis`); `pickPreferredVoice()` scans `speechSynthesis.getVoices()` for a known-calm female English voice by name (Samantha, Ava, Zira, the common Microsoft neural voices like Aria/Jenny/Sonia, etc., preferring an "enhanced"/"premium"/"neural" variant of that name if one exists, with a `/female/i` name match as final fallback), since the API doesn't expose gender/tone/quality as queryable properties — voice availability and quality are entirely device/OS-dependent, so which one actually gets used varies. This is the free browser TTS, not a paid neural voice API. `speakStep()` reads a step's title and instructions as two separate queued utterances rather than one concatenated sentence, so the engine gives each its own intonation arc instead of a flat run-on read; `speak()` (used for live-feedback text) stays single-utterance. Both share `speakUtterance()`'s rate/pitch (`0.93`/`0.97`, slightly slowed and lowered from the engine default for a calmer read).

**Finish & review**: `#finish-review-btn` on the live screen opens `#review-overlay` at any point in the routine (not just the last step) — an optional photo capture (downscaled to 480px max dimension, JPEG quality 0.75, to keep it small in `localStorage`) plus a description textarea. Either "Save to my guides" or "Skip photo & description, just save" writes the same routine object `save-look-btn` writes, with `photo` (a data URL) and `description` added, then lands on the done screen with `save-look-btn` already marked saved (so the two save paths never double-save the same routine). `renderAccountView`'s routine list renders `r.photo`/`r.description` when present — both are generated/typed locally and never sent anywhere.

**Live feedback ("Check my progress")**: captures the current video frame to a hidden `<canvas>`, downscaled to a 480px max dimension (same cap `captureReviewPhoto` uses) so the upload stays small and the round-trip stays fast, un-mirrors it (camera preview is CSS-mirrored via `scaleX(-1)` for a natural selfie view, but the captured frame is flipped back before sending so Claude sees it right-reading), and sends it plus a step-aware coaching prompt to `callClaude`. The spoken/text feedback is rendered in `#feedback-card` and read aloud if enabled.

## Conventions

- Keep everything in `index.html` unless a change specifically needs new server-side logic — this project intentionally has no build step, and splitting JS/CSS into separate files would require introducing tooling that doesn't exist yet.
- CSS uses custom properties defined once on `:root` (colors, radius) — reuse those variables (`--bg`, `--surface`, `--surface-2`, `--ink`, `--muted`, `--pink`, `--line`, `--good`) rather than hardcoding new colors. The palette is white background (`--bg`), baby-pink card surfaces (`--surface`/`--surface-2`), black text/borders (`--ink`/`--line`), and a neon pink (`--pink`) reserved for CTAs, active states, and highlights — the "sticker" look (thick black borders, hard black offset `box-shadow`s) works because those shadows/borders are hardcoded black regardless of theme, so the variable-driven approach means most components repaint correctly from the tokens alone when the palette changes.
- No emoji anywhere in the UI — functional icons (tab bar, contact open) are inline SVG line icons matching the face-diagram's hand-drawn stroke style (`stroke:currentColor; fill:none; stroke-width:1.7-2`), not emoji glyphs. Plain typographic symbols (★/☆ for ratings, ✕ for close, ✓ for saved, ←/→ for navigation) are fine and not considered emoji — they render as simple glyphs, not colorful pictographs.
- All Claude prompts request a specific, strict output contract (plain text for coaching feedback, fenced-free JSON for step generation) and the client code parses that contract directly — if you change a prompt's expected output shape, update the corresponding parsing code (`stripFences`/`JSON.parse` for steps, plain `.trim()` for feedback text) in the same change.
- `api/claude.js` is intentionally a dumb passthrough (no prompt logic, no validation beyond method/error checks) — put all prompt engineering in `index.html`, not in the serverless function.
- Any AI-generated or user-typed text that gets inserted via `.innerHTML` (saved-routine steps, reviews, the face-diagram caption) must go through `escapeHtml()` first — `.textContent`/`.value` assignments don't need it, since those never parse HTML. This matters more than it looks like it should: `state.occasion` in particular went from a fixed set of chip labels to free-typed text once the "Other" occasion field was added, so anywhere it's rendered as markup needs the same treatment.
