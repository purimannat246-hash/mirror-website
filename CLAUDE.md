# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Glomi" is a single-page prototype for a live AI makeup coach. A user picks an occasion (or a curated look), Claude generates a step-by-step routine and the shopping list it requires, and then a camera-based "live" screen lets them ask Claude to look at a captured frame and give spoken feedback per step.

The repo is two code files, a setup README, and a small folder of photos:
- `index.html` — the entire frontend: markup, CSS, and vanilla JS all inline in one file. No framework, no bundler, no build step.
- `api/claude.js` — a single Vercel serverless function that proxies requests to the Anthropic Messages API, keeping `ANTHROPIC_API_KEY` server-side.
- `README.md` — end-user instructions for uploading this repo to GitHub, deploying it on Vercel, and wiring up the API key/domain. It is not developer documentation.
- `images/looks/` — real photos used as the Looks gallery card art (see the Looks tab entry below). Static files, served as-is by Vercel; no processing pipeline.

There is no `package.json`, no dependency manifest, and no test/lint/build tooling anywhere in the repo — there are no such commands to run. Development is just editing `index.html` and `api/claude.js` directly and deploying to Vercel to test.

## Architecture

**Deployment model**: static file (`index.html`) + one serverless function (`api/claude.js`), deployed on Vercel with zero config. Vercel auto-detects any file under `api/` exporting a default handler as a serverless function; `index.html` is served as a static asset. The API key lives only in the Vercel project's environment variables (`ANTHROPIC_API_KEY`), never in client code.

**Client → server → Anthropic flow**: the frontend never calls Anthropic directly. Two helpers in `index.html` both POST to `/api/claude`: `callClaude(content)` sends `{ content }` for single-turn calls (step generation, live vision feedback, the substitute swap), while `callClaudeMessages(messages, system)` sends `{ messages, system }` directly for the multi-turn chat widget. `api/claude.js` reads `content`/`messages`/`system` from the body — `messages` is used as-is if present, otherwise it wraps `content` as `[{ role: 'user', content }]` — forwards that to `https://api.anthropic.com/v1/messages` with the server-side key, model `claude-sonnet-5`, and `max_tokens: 4096`, and relays the raw Anthropic response (or error) back to the client. `content` (or a message's `content`) can be plain text or a mixed array of `{type: "text"}` / `{type: "image", source: {type: "base64", ...}}` blocks — the API function is a thin, opinion-free passthrough, so all prompt construction and response parsing happens client-side.

**Tab bar**: a fixed bottom `.tabbar` with three tabs — Home, Looks, Account — toggles `#home-view` / `#looks-view` / `#account-view` via `switchTab()` and the `TAB_VIEWS` map, following the same `.hidden`-class pattern as everything else (no router). The tab bar itself is hidden during the focused loading/live-guide flow (`setTabbarVisible(false)`) and restored on the done screen or when returning to setup, so it can't be used to abandon an in-progress guide.

**App state machine** (inside `#home-view`): a single global `state` object (`occasion`, `neededProducts`, `steps`, `currentStep`, `stream`) drives five screens toggled via the `.hidden` class — `#setup-screen` → `#loading-screen` → `#shopping-list-screen` → `#live-screen` → `#done-screen`. DOM elements are looked up by ID on demand rather than cached. `setupChipGroup(containerId, onSelect)` scopes the occasion chips' "clear siblings, mark active" logic to their own container so it can be reused for other chip groups without them interfering with each other.

**Chat widget ("Ask Glomi")**: a floating button (`#chat-fab`, hidden alongside the tab bar during the loading/live-guide flow) opens `#chat-overlay`, a free-form conversation independent of the guided flow. History is a plain `{role, content}` array persisted to `localStorage` (`glomi_chat`) via `getChatHistory`/`setChatHistory`, sent through `callClaudeMessages` with `CHAT_SYSTEM_PROMPT` as the `system` param — this is the one place in the app that needs real multi-turn context, which is why `callClaudeMessages`/the `messages`+`system` API shape exists. `setChatHistory` trims what's stored to the last `CHAT_HISTORY_LIMIT` messages, and each send only sends the last `CHAT_API_WINDOW` messages to the API, so neither the DOM re-render, the localStorage write, nor the API request payload grows unbounded as a conversation gets long. Rendered chat bubbles run user and assistant text through `escapeHtml` before insertion — unlike the rest of the app, this is free-form user-typed text going into `innerHTML`, so escaping isn't optional here.

**Looks tab**: a hardcoded `LOOKS` array (id, name, occasion tag, art variant, description, suggested products, optional `pro:true`) — currently Bold Glam, Clean Girl, and Golden Hour Glam, none currently flagged `pro:true`; `renderLooksGrid()` renders every entry as an identical `.look-card` in a uniform 2-column `.looks-grid`. The card art is a real photo per look (`images/looks/<variant>.jpg`, e.g. `bold-glam.jpg`), set as a CSS `background-image` on `.look-art.<variant>` (`background-size:cover`, with a per-look `background-position` override where the default center crop cuts off the face awkwardly, e.g. `.clean-girl`). There is no image generation or licensing pipeline — photos are supplied directly by whoever's maintaining the site and dropped into `images/looks/`; picking new photos means resizing them (long edge ~900px is plenty for a card this size) and confirming there's an actual license to use them before adding. Tapping a card opens `#look-detail-overlay`; its "Use this look" button jumps to the Home tab, pre-selects the matching occasion chip (revealing Everyday/Other first if the look's tag is one of those), and sets `state.lookStyle` (`{name, desc, products}`) — shown as a dismissible `#active-look-badge` on the setup screen ("Building your Bold Glam look"). When set, the step-generation prompt (below) is told to build around that specific look's style rather than a generic version of the occasion, so picking "Bold Glam" actually produces a bold, dramatic routine instead of the same routine any other Party pick would get. Manually tapping any occasion chip afterward clears `state.lookStyle` so it can't silently leak into an unrelated routine.

**Account tab and local persistence**: there is no login system or backend database. Favourited looks, saved routines, and reviews are all read/written straight to `localStorage` via the `getFavorites`/`getRoutines`/`getReviews` (and matching `set*`) helpers — data lives on-device only and does not sync across browsers or devices. The Account tab itself has no profile/name/email fields — `getAccount()`'s `name`/`email` are only ever written from the checkout form (below), on the theory that collecting contact details is only worth doing for someone actually paying, not every visitor. "Save this look" on the done screen snapshots `state.occasion`/`state.neededProducts`/`state.steps` into the `glomi_routines` list. "Upgrade" opens a preview checkout sheet (`#checkout-overlay`, styled off the same `.look-detail-overlay`/`.look-detail-card` pattern as the Looks detail sheet) with name, email, and full card-details fields — but the card number/expiry/CVC are deliberately never persisted or sent anywhere; only the last 4 digits are kept in `localStorage` (on `glomi_account.plan`/`cardLast4`) purely for display, the same as what a real processor like Stripe would expose after checkout, while `name`/`email` are saved to `glomi_account` so Pro can recognize the account on return. There is no real billing integration yet — this is intentionally a stand-in for a future Stripe Checkout redirect, not a payment form to be taken further as-is.

**Free-plan limits**: `isProAccount()` (`getAccount().plan === 'pro'`) gates saved guides (`canSaveMoreGuides()`, checked in both `save-look-btn` and `saveReviewedLook()` before writing to `glomi_routines`, capped at `FREE_GUIDE_LIMIT`), daily chat messages (`getChatUsageToday()`/`incrementChatUsageToday()`, a `{date, count}` pair in `localStorage` that resets whenever the stored date isn't today, capped at `FREE_CHAT_LIMIT`), and any `LOOKS` entry flagged `pro:true` (gated in `openLookDetail()`, which swaps the normal "Use this look"/favourite buttons for an "Upgrade to unlock" button when locked — none of the current looks carry the flag, but the mechanism stays wired up for the next one that does). Every limit is a soft, client-side check only — there's no server to enforce it, so it's an honest nudge (and a reason to upgrade), not a real paywall; clearing local storage resets all of it. Hitting a limit shows an inline message with a link that jumps to Account and opens the checkout sheet (`showSaveLimitMessage()` for guides, an inline bubble in `sendChatMessage()` for chat).

**Community reviews** (bottom of the setup screen): four hardcoded testimonial cards (name, star rating, quote) — two 5-star, one 3-star, one 2-star, a deliberately mixed spread rather than an all-positive wall — explicitly labeled "Example reviews from early testers of this prototype." This is static marketing content, not a real review feed — there's no backend for reviews to sync across visitors, so a genuine public wall would need a real database, which doesn't exist yet.

**Setup screen**: user picks an occasion chip — there is no product input at all; the app tells the user what they'll need rather than asking. Only School/Date/Party show by default, each with `class="chip hidden"` on Everyday/Other until `#occasion-more-btn` is tapped (a plain toggle over `.classList.toggle('hidden')` on those two chips — no animation, just a label flip between "▾ More options"/"▴ Fewer options"). Picking "Other" reveals `#occasion-other-input`, a free-text field whose value (not the literal word "Other") becomes `state.occasion`, giving the AI real context ("prom", "photoshoot") instead of a vague placeholder.

**Step generation**: on "Start my live guide", a prompt asking for a JSON object with `productsNeeded` (a flat array of product names the routine requires) plus an ordered `steps` array (`title`, `instructions`, `product`, `zone`, `markerCount`, `diagramNote`, `color` per step) is sent via `callClaude` — since there's no product input, Claude both decides what a beginner needs for the occasion *and* builds the routine around it in one call. The prompt also spells out an intensity/finish guide per occasion (School/Everyday light and low-maintenance, Date soft and romantic, Party bold with glitter/shimmer and long-wear or waterproof formulas called out) so the routine actually matches what the occasion calls for instead of defaulting to the same safe, natural look regardless of `state.occasion` — this is prompt text only, not something the client parses or validates. `color` is Claude's best-guess hex shade for that product (a red lipstick → a red, a nude concealer → beige) and is validated with a `/^#[0-9a-fA-F]{6}$/` check before use — an invalid or missing value just falls back to the default pink marker fill rather than breaking rendering. The response is stripped of markdown code fences (`stripFences`) and `JSON.parse`d into `state.steps`/`state.neededProducts`. Claude is expected to return *only* raw JSON — if that contract breaks (extra prose, invalid JSON), generation fails and the user is bounced back to the setup screen with an error message. There is no retry or schema validation beyond the `try/catch`.

**Shopping list screen**: sits between loading and the live guide, showing `state.neededProducts` as plain tags (`renderNeededProducts()`) before the user commits to starting — "Got it, let's start" is what actually shows the live screen and starts step rendering.

**Substitute swap**: on the live screen, "Don't have this? Get a swap" (`#substitute-btn`) sends a one-off `callClaude` text prompt scoped to the current step's product, asking for one common alternative already lying around plus a one-sentence usage tip — rendered into `#substitute-result`, which resets to hidden on every step change (`renderStep()`) so a stale swap suggestion from a previous product never lingers into the next step.

**Live screen**: shows a circular camera preview (`getUserMedia`), the current step's text, and an SVG face diagram (`#face-diagram`) with dot markers placed according to `zoneCoords` (a hand-authored map of named face zones — `forehead`, `brows`, `eyelids`, `under-eyes`, `cheeks`, `nose`, `lips`, `jawline`, `chin`, `all-over` — to `[x, y]` coordinates on a 200×240 viewBox). `getMarkerPoints` spreads multiple markers per zone outward in rings when `markerCount` exceeds the zone's base point count. Steps can optionally be read aloud via the Web Speech API (`speechSynthesis`); `pickPreferredVoice()` scans `speechSynthesis.getVoices()` for a known-calm female English voice by name (Samantha, Ava, Zira, etc., preferring an "enhanced"/"premium"/"neural" variant of that name if one exists, with a `/female/i` name match as final fallback), since the API doesn't expose gender/tone/quality as queryable properties — voice availability and quality are entirely device/OS-dependent, so which one actually gets used varies. This is the free browser TTS, not a paid neural voice API.

**Finish & review**: `#finish-review-btn` on the live screen opens `#review-overlay` at any point in the routine (not just the last step) — an optional photo capture (downscaled to 480px max dimension, JPEG quality 0.75, to keep it small in `localStorage`) plus a description textarea. Either "Save to my guides" or "Skip photo & description, just save" writes the same routine object `save-look-btn` writes, with `photo` (a data URL) and `description` added, then lands on the done screen with `save-look-btn` already marked saved (so the two save paths never double-save the same routine). `renderAccountView`'s routine list renders `r.photo`/`r.description` when present — both are generated/typed locally and never sent anywhere.

**Live feedback ("Check my progress")**: captures the current video frame to a hidden `<canvas>`, downscaled to a 480px max dimension (same cap `captureReviewPhoto` uses) so the upload stays small and the round-trip stays fast, un-mirrors it (camera preview is CSS-mirrored via `scaleX(-1)` for a natural selfie view, but the captured frame is flipped back before sending so Claude sees it right-reading), and sends it plus a step-aware coaching prompt to `callClaude`. The spoken/text feedback is rendered in `#feedback-card` and read aloud if enabled.

## Conventions

- Keep everything in `index.html` unless a change specifically needs new server-side logic — this project intentionally has no build step, and splitting JS/CSS into separate files would require introducing tooling that doesn't exist yet.
- CSS uses custom properties defined once on `:root` (colors, radius) — reuse those variables (`--bg`, `--surface`, `--surface-2`, `--ink`, `--muted`, `--pink`, `--line`, `--good`) rather than hardcoding new colors. The palette is white background (`--bg`), baby-pink card surfaces (`--surface`/`--surface-2`), black text/borders (`--ink`/`--line`), and a neon pink (`--pink`) reserved for CTAs, active states, and highlights — the "sticker" look (thick black borders, hard black offset `box-shadow`s) works because those shadows/borders are hardcoded black regardless of theme, so the variable-driven approach means most components repaint correctly from the tokens alone when the palette changes.
- No emoji anywhere in the UI — functional icons (tab bar, chat send/open, the favourite-look heart) are inline SVG line icons matching the face-diagram's hand-drawn stroke style (`stroke:currentColor; fill:none; stroke-width:1.7-2`), not emoji glyphs. Plain typographic symbols (★/☆ for ratings, ✕ for close, ✓ for saved, ←/→ for navigation) are fine and not considered emoji — they render as simple glyphs, not colorful pictographs.
- All Claude prompts request a specific, strict output contract (plain text for coaching feedback, fenced-free JSON for step generation) and the client code parses that contract directly — if you change a prompt's expected output shape, update the corresponding parsing code (`stripFences`/`JSON.parse` for steps, plain `.trim()` for feedback text) in the same change.
- `api/claude.js` is intentionally a dumb passthrough (no prompt logic, no validation beyond method/error checks) — put all prompt engineering in `index.html`, not in the serverless function.
- Any AI-generated or user-typed text that gets inserted via `.innerHTML` (chat bubbles, saved-routine steps, reviews, the face-diagram caption) must go through `escapeHtml()` first — `.textContent`/`.value` assignments don't need it, since those never parse HTML. This matters more than it looks like it should: `state.occasion` in particular went from a fixed set of chip labels to free-typed text once the "Other" occasion field was added, so anywhere it's rendered as markup needs the same treatment.
